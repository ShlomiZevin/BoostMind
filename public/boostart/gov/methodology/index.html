1. מטרת המסמך ועקרונות יסוד

מסמך זה מגדיר את שיטת העבודה של Boostart לפיתוח אפליקציות WEB באמצעות Agentic AI ו-Spec-Driven Development, להלן SDD. השיטה מיועדת לסביבות ממשלתיות וארגוניות שבהן נדרשים בקרה, אבטחת מידע, תיעוד, תחזוקתיות ויכולת ביקורת מלאה.

  • ה-Spec הוא מקור האמת. קוד, בדיקות, תיעוד ותצורות נגזרים ממנו.
  • אדם מוסמך מחזיק באחריות לכל החלטה ולכל שורת קוד שנמסרת.
  • מידע אמיתי, מידע רגיש וסודות אינם מועברים למודלים מחוץ לסביבה המבודדת והמאושרת.
  • השיטה Tool-agnostic. התוצרים נשמרים ב-Repository ואינם תלויים בכלי AI מסוים.
  • לכל שינוי קיימת שרשרת Traceability מדרישה עסקית ועד PR, בדיקה ואישור אנושי.
  • הקוד הנמסר קריא, מתועד וניתן לתחזוקה על ידי צוות המשרד גם ללא כלי AI.
  • סוכן AI אינו בעל סמכות לאשר את עבודתו, לשנות סביבת ייצור או להחליף שיקול דעת מקצועי.
  • תיקון קוד מתחיל בעדכון ה-Spec. אין תיקוני קוד ישירים שיוצרים פער בין הדרישה לבין המימוש.

השימוש ב-Agentic AI נועד להאיץ עבודה מובנית ומבוקרת. הוא אינו משנה את חובת התכנון, הבדיקה, הסקירה והאישור האנושי.

6. החוקה הפרויקטלית, Project Context ו-Skills

החוקה הפרויקטלית היא מסמך מחייב שנמצא ב-Repository ונקרא בתחילת כל Session של Agent. היא מגדירה את כללי העבודה שהסוכנים והמפתחים נדרשים לפעול לפיהם.

  • מטרות המערכת, גבולותיה ובעלי התפקידים המאשרים.
  • החוקה הממשלתית והחוקה של המשרד, לאחר קבלתן והטמעתן בפרויקט.
  • כללי אבטחת מידע, פרטיות, יה"ב, הרשאות וטיפול בסודות.
  • כללי פיתוח, ארכיטקטורה, naming, Code Review ותיעוד.
  • מדיניות שימוש בכלי AI, מודלים, Context ונתונים.
  • כללי עבודה מול Nimbus, אזור נחיתה, CI/CD ו-IaC.
  • כללי נגישות AA ודיזיין סיסטם ממשלתי.
  • כללי רישוי, SBOM, סריקות אבטחה וניהול תלויות.
  • שערי HITL, פעולות אסורות ותנאי עצירה.
  • מבנה ה-Repository, שיטת ניהול ADRs ומזהי דרישות.

Project Context הוא אוסף ממוקד של מסמכים, החלטות, קוד ודוגמאות המועבר לסוכן עבור משימה מוגדרת. הוא קטן ככל האפשר, מעודכן, ומכיל רק מידע שנדרש להשלמת המשימה באופן מדויק.

Skills הם הוראות עבודה חוזרות, גרסאות ומבוקרות, עבור משימה מקצועית מוגדרת. Skill מתאר קלט, שלבים, כללי איכות, פלט צפוי ותנאי עצירה.

7. Guardrails לסוכני הפיתוח

  • כל Agent פועל בהרשאת least privilege ובסביבה מבודדת.
  • לסוכנים אין credentials לייצור, ואין להם גישה ישירה ל-Production DB.
  • כתיבה ל-Production DB מתבצעת רק דרך Pipeline מאושר ובאישור אנושי מפורש.
  • מחיקת משאבים, שינויי IaC ופעולות בלתי הפיכות מחייבים G4.
  • רק כלים, פקודות, Repositories וחבילות שנכללו ב-allow-list זמינים לסוכן.
  • סודות, מפתחות, tokens וקבצי credentials אינם נכנסים ל-Context של מודל.
  • נתיבים רגישים, קבצי תצורה והגדרות הרשאה מוגנים מפני שינוי אוטומטי.
  • תעבורת רשת יוצאת מוגבלת ליעדים ולשירותים שאושרו מראש.
  • מוגדרים תקציב tokens, מגבלת זמן ומגבלת פעולות לכל משימה.
  • תנאי עצירה מחייבים את הסוכן לעצור במקרה של אי-ודאות, חריגת הרשאה, כשל בדיקה או סתירה ב-Spec.
  • שינוי שאינו ניתן להסבר באמצעות Spec, Diff ובדיקה אינו מתקדם למיזוג.
  • אין שימוש בפקודות הרסניות ללא אישור אנושי מפורש ותיעוד הפעולה.

8. ניהול זיכרון וקונטקסט

ניהול Context הוא רכיב מרכזי בפיתוח ארוך טווח באמצעות Agents. חלון הקונטקסט של מודל אינו משמש כמקור זיכרון יחיד, ולכן הזיכרון נשמר במבנים מבוקרים ב-Repository ובמערכות מאושרות.

  • ה-Repository הוא הזיכרון ארוך הטווח: החוקה, Specs, ADRs, החלטות, בדיקות, תיעוד ו-PRs.
  • במערכות Legacy גדולות ניתן להקים אינדקס Vector של קוד ומסמכים לצורכי Discovery וחיפוש מבוקר.
  • לכל משימה נבנה Context Pack הכולל רק את הדרישה, הקוד, החוזים וההחלטות הרלוונטיים.
  • כל Session מסתיים ב-Handoff Note המתעד מה בוצע, מה נותר, אילו החלטות התקבלו ואילו סיכונים זוהו.
  • החלטות ארכיטקטוניות אינן נשמרות רק ב-Chat. הן מתועדות ב-ADR בעל מזהה וסטטוס.
  • מידע שהתיישן מסומן ככזה או מוסר מה-Context כדי למנוע שימוש בהנחות ישנות.

מבנה זה מונע אובדן הקשר בין Sessions, הפקת קוד על בסיס החלטות שהתבטלו, וסטייה הדרגתית בין ה-Spec לבין המימוש. הוא מאפשר לצוות אנושי להמשיך עבודה גם אם הוחלף כלי AI או מודל.

9. תיעוד, Observability ו-Traceability של עבודת הסוכנים

כל פעולת Agent מתועדת לצורך ביקורת תקציבית, אבטחתית ומקצועית. הלוגים נשמרים בסביבת הענן של המשרד, בהתאם למדיניות השמירה והגישה שתוגדר בפרויקט, לדוגמה CloudWatch ב-AWS או Cloud Logging ב-GCP.

  • מזהה Session, מזהה Agent, מזהה משימה ומזהה דרישה.
  • גרסת החוקה, ה-Spec, ה-Skill וה-Context Pack ששימשו לפעולה.
  • Prompt שנשלח, בכפוף להסרת סודות ומידע שאסור לתעד.
  • Tool calls, פקודות שבוצעו, קבצים שנקראו וקבצים ששונו.
  • תשובת המודל, פלט מעובד, שגיאות ותנאי עצירה.
  • ספק המודל, שם המודל, גרסה, tokens, משך פעולה ועלות.
  • branch, Worktree, Diff, PR ותוצאות בדיקות קשורות.
  • זהות הסוקר האנושי, החלטת האישור והסבר במקרה של דחייה.
  • פעולות חריגות, ניסיונות גישה חסומים והפרות Guardrails.

מזהה דרישה → משימה → סשן סוכן → PR → סוקר אנושי → בדיקות

שרשרת זו מאפשרת לאתר במהירות מדוע נכתב רכיב מסוים, על איזה Spec הוא מבוסס, איזה Agent סייע ביצירתו, ומי קיבל את החלטת האישור. היא גם מאפשרת ניתוח עלויות AI לפי רכיב, משימה, מודל או צוות.

ניסיון בבניית מערכות multi-agent כולל תיעוד Prompts ופלטים, כללים דטרמיניסטיים לצד המודל, וזיהוי ספק המודל, המודל, ה-tokens ומשך הפעולה. עיקרון זה מיושם גם בפרוטוקול הפיתוח, בהתאמות הנדרשות למדיניות המשרד.

10. פרטיות ואבטחת מידע בעבודה עם AI

  • מודלים נצרכים רק דרך חשבון הענן של המשרד, באמצעות Bedrock, Vertex AI או מסלול Nimbus מאושר אחר.
  • אין הזנת מידע סודי, אישי, רגיש או מידע אמיתי לכלי SaaS חיצוני שאינו מבודד ומאושר.
  • סביבות Development ו-Test אינן כוללות נתוני ייצור. הן משתמשות בנתונים סינתטיים.
  • מידע אישי עובר PII redaction לפני תיעוד, אינדוקס, Eval או העברה למודל.
  • קבצי secrets, מפתחות API, certificates ו-credentials אינם נכללים ב-Prompt, בלוגים או ב-Vector DB.
  • כל כלי AI, Plugin, MCP Server ומודל עוברים allow-list לפני שימוש.
  • נלמד ונפעל לפי מדיניות יה"ב לסוכנים, לאחר קבלתה בפרויקט, ולפי החוקה הממשלתית הרלוונטית.
  • הרשאות גישה, retention של לוגים ומיקום נתונים מוגדרים יחד עם גורמי אבטחת המידע.
  • פעולות Agent ניתנות לאיתור, לביקורת ולחסימה באמצעות Guardrails ותצפיתיות.
  • במקרה של חשד לחשיפת מידע, ה-Agent נעצר, האירוע מתועד ומטופל לפי נוהל אירועי אבטחה של המשרד.

12. איכות קוד שנוצר ב-AI

בדיקות

כל מימוש כולל בדיקות הנגזרות מקריטריוני הקבלה ב-Spec. הבדיקות נכתבות ומורצות ב-CI/CD, אך התרחישים, מקרי הקצה והמשמעות העסקית שלהם מאושרים גם על ידי גורם אנושי.

  • Unit tests ללוגיקה, כללים, המרות וחריגים.
  • API tests אוטומטיים בסגנון Postman או כלי מקביל, לפי חוזי API.
  • UI ו-E2E tests לתרחישים עסקיים מרכזיים.
  • Visual tests לרכיבי UI, RTL, דיזיין סיסטם ונגישות.
  • Integration tests לאינטגרציות, תורים, תהליכים אסינכרוניים והרשאות.
  • Regression tests לכל תקלה שתוקנה ולכל שו"ש משמעותי.

כיסוי אינו נמדד רק כאחוז שורות קוד. הוא נמדד גם לפי תרחישים עסקיים, חריגים, הרשאות, מעברי מצב, כשלי אינטגרציה ומקרי קצה. Human Reviewer בודק במיוחד שבדיקות שנוצרו ב-AI אינן בודקות רק את ההתנהגות שהקוד עצמו מימש.

חולשות אופייניות לקוד AI

קוד שנוצר על ידי מודל עלול לכלול API מיושן, תלות לא מתועדת, טיפול חסר בשגיאות, לוגיקה שנראית תקינה אך נכשלת במקרי קצה, או שימוש בלתי בטוח בקלט משתמש. לכן נדרשת בדיקה ייעודית מעבר להרצת tests.

  • שימוש ב-API מיושן
  • SQL או command injection
  • הרשאה חסרה או רחבה
  • טיפול שגיאות חלקי
  • לוגיקה סמויה לא מתועדת
  • תלות לא מאושרת
  • קוד שלא נקרא
  • שכפול קוד גנרטיבי
  • race conditions
  • ולידציה חסרה לקלט

Reviewer Agent מסמן ממצאים, אך Human Reviewer מחויב להבין את הלוגיקה, את השפעתה ואת התיקון. קוד שלא ניתן להסבר על ידי הסוקר אינו מאושר.

יעילות ועלות ענן

בכל PR נבדקת יעילות בסיסית של גישות למסד הנתונים, APIs, cache, streaming, פעולות רקע ושימוש במשאבי ענן. Agentic AI עלול לייצר קריאות חוזרות או שכבות מיותרות שנראות תקינות פונקציונלית אך מגדילות עלויות ותלות.

נבדקים בין היתר שאילתות ללא אינדקס, N+1 queries, polling מיותר, קריאות API כפולות, טעינת מידע עודף, retries לא מבוקרים ולולאות ללא גבול. ממצאים מהותיים נרשמים ב-PR או ב-ADR.

תחזוקתיות ותיעוד ברמת המתודה

נבדקים קריאות קוד, הפרדת אחריות, naming, גבולות בין שכבות, טיפול בשגיאות, testability, ומדדי תחזוקתיות שייקבעו בפרויקט. אין להשאיר קוד מת, פיצול לא מוסבר של לוגיקה, או שכפול שנוצר כתוצאה מעבודה מקבילית של Agents.

מתודות ציבוריות, חוזי API, כללים עסקיים ותהליכים מורכבים מתועדים ברמת המתודה או הרכיב, כאשר התיעוד מוסיף הסבר שאינו מובן מאליו מהקוד. התיעוד מתעד את ה"למה", ולא רק את ה"מה".

זכויות יוצרים ורישוי

כל תלות חדשה עוברת בדיקת רישוי. קוד ותלויות בעלי רישיון מגביל כגון GPL או AGPL אינם נכנסים לפרויקט ללא החלטה מפורשת של המשרד והגורמים המוסמכים.

מופק SBOM כחלק מתהליך המסירה וה-Release. סריקת רישוי ב-CI/CD בודקת גם תלות טרנזיטיבית, גרסאות פגיעות והכנסת חבילות לא מאושרות.

13. שכבת ה-AI במערכות שנמסרות

כאשר המערכת הנמסרת כוללת Agents או יכולות GenAI, שכבת ה-AI מתוכננת כרכיב מערכת מבוקר ולא כאוסף קריאות ישירות למודל. היא כוללת הפרדה בין לוגיקה עסקית, ספקי מודלים, מידע, הרשאות, מדידה ובקרה.

AI Gateway

  • ניתוב מודלים לפי משימה, מדיניות, עלות, זמינות ורגישות מידע.
  • fallback ו-retry מבוקרים, עם מגבלות למניעת לולאות ועלויות בלתי צפויות.
  • ניהול מפתחות והרשאות ללא חשיפתם ללקוח או ל-Agent.
  • rate limits לפי משתמש, שירות, Agent או תהליך.
  • caching כאשר התשובה מותרת לשימוש חוזר ואינה כוללת מידע אישי.
  • token tracking, עלות לפי בקשה, תקציב והתראות.
  • PII redaction לפני שליחה למודל ולפני שמירת לוגים.
  • Tracing של בקשות, מודלים, כלים, Latency, עלות ותוצאות.

MCP Gateway/Registry ו-Guardrails

MCP Gateway או Registry מרכזים את הגישה לכלים חיצוניים. כל MCP Server נרשם, עובר בדיקת אבטחה, מוגדר עם הרשאות מצומצמות, ומנוהל לפי allow-list.

Guardrails נאכפים לפני ואחרי קריאת המודל. הם כוללים בדיקת הרשאות, סינון מידע רגיש, הגבלת כלי פעולה, ולידציה של פלט מובנה, כללים עסקיים, חסימת הוראות אסורות וניתוב לאישור אנושי במקרים נדרשים.

Evals ו-Eval Suite

Eval Suite כולל Test Dataset גרסאי, הכולל תרחישים רגילים, מקרי קצה, קלטים בעייתיים, שיחות מדומות ודוגמאות מאושרות. כל שינוי ב-Spec, Prompt, Agent, מודל או כלי מחייב הרצת Evals רלוונטיים.

Evals משמשים Quality Gate ב-CI/CD עבור רכיבי AI. שינוי שאינו עומד בספי האיכות שנקבעו לפרויקט אינו מתקדם לפרסום או לייצור ללא החלטה אנושית מתועדת.

Specs, Prompts, Agents וכללי Guardrails הם גרסאות מנוהלות. פרסום שינוי הוא פעולה נפרדת משמירה. ניתן לשמור Draft, לבצע Review, להריץ Evals, ורק לאחר אישור לבצע publish לגרסה פעילה.

FinOps כולל תקציבי tokens, מגבלות עלות, התראות על חריגה, דוחות שימוש ו-kill-switch להשבתת Agent, כלי, מודל או מסלול פעולה. פעולות בעלות השפעה גבוהה מוגדרות מראש עם fallback אנושי.

ניסיון בבניית מערכות multi-agent כולל תפקידים מופרדים, Agents משורשרים, Context מופעל, מערכות זיכרון, RAG, כללים דטרמיניסטיים לצד מודל, תיעוד Prompts ופלטים, וניתוב בין מספר ספקי מודלים.

14. Best Practices לפיתוח עם AI

  • מפרקים עבודה למשימות קטנות וברורות.
  • מקצים משימה אחת לכל Session של Agent.
  • כותבים קריטריוני קבלה לפני כתיבת קוד.
  • מצרפים לכל משימה Context Pack ממוקד.
  • לא מקבלים קוד שלא ניתן להסביר ולתחזק.
  • לא נותנים ל-Agent לאשר את עבודתו.
  • מעדכנים Spec לפני כל תיקון מהותי.
  • מריצים בדיקות לפני Code Review.
  • בודקים מקרי קצה אנושיים לבדיקות שנוצרו ב-AI.
  • שומרים החלטות ב-ADR ולא רק בשיחה.
  • משתמשים ב-branch או Worktree מבודד לכל עבודה מקבילה.
  • חוסמים סודות, נתונים אמיתיים ופעולות ייצור מה-Context.
  • מודדים עלות, tokens ומשך פעולה של Agents.
  • מעדכנים תיעוד יחד עם הקוד ולא לאחר המסירה.
  • מבצעים publish נפרד משמירת Draft ברכיבי AI.
  • מעדיפים כללים דטרמיניסטיים כאשר ניתן להגדיר כלל עסקי מפורש.

15. העברת ידע והטמעה במשרד

העברת הידע מתבצעת תחילה בהדרכה פרונטלית לצוותי המשרד והספקים המעורבים, בהתאם להעדפת המכרז. לאחר מכן היא נמשכת בעבודה משותפת על Specs, PRs, שערי איכות ותרחישי מסירה.

במשרד שבו טרם קיימים תהליכי AI מוסדרים, נתחיל בהכנת תשתית העבודה: מיפוי בעלי תפקידים, בחירת סביבה מאושרת, הגדרת הרשאות, לוגים, מדיניות נתונים, כללי HITL, תהליך אישור כלים והקמת תבניות עבודה. המטרה היא לאפשר לצוות המשרד להמשיך לתחזק, לפתח ולבקר את המוצר באופן עצמאי.
