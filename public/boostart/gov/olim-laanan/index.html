1. תקציר

אנו מציעים להמשיך את פיתוח מערכת "עולים לענן" כתהליך מבוקר של SDD, המשלב סוכני AI בכל שלבי ה-SDLC, לצד שערי איכות ואישור אנושי בנקודות החלטה. העבודה תבוצע בתיאום מלא עם צוות מערך הדיגיטל הלאומי, ה-CCoE, מנהל המוצר, ארכיטקט המשרד ונציגי אבטחת המידע.

נקודת המוצא היא המערכת הקיימת. נמשיך את בסיס הקוד הקיים ב-Next.js וב-React, את תשתית הבדיקות ב-Playwright ואת הפריסה על AWS בנימבוס. לא נחליף את המערכת ולא נבצע כתיבה מחדש ללא צורך מוכח ואישור המשרד. כל הרחבה תתבסס על Discovery, הבנת המודולים והאינטגרציות הקיימים, ואישור Spec לפני מימוש.

המערך יקבל קוד מקור מתועד, בדיקות אוטומטיות, מסמכי Spec קריאים בעברית, תיעוד ארכיטקטוני ותהליך CI/CD מלא. הידע והתוצרים יישארו בסביבה המשותפת ובבעלות המשרד. הקוד יישאר קריא ותחזוקתי גם לצוות שיבחר להמשיך לפתח אותו ללא כלי AI.

2. הבנת המערכת והצורך

מערכת "עולים לענן" היא כלי תפעולי ומקצועי למימוש מפת הדרכים הממשלתית לשנים 2025–2029 ולהחלטת ממשלה 231. היא מרכזת את נתוני המערכות המיועדות למעבר לנימבוס, ומאפשרת לנהל תהליך אחיד, מתועד ומבוקר עבור משרדי הממשלה, יחידות הסמך והגופים הרלוונטיים.

ליבת המערכת היא התאמת דרישות המעבר למאפייני כל מערכת. המערכת אוספת נתונים לצורך סיווג מידע וקביעת רמת ההגנה הנדרשת. על בסיס הסיווג, מאפייני המערכת והסיכונים, היא מפיקה בקרות אבטחת מידע מותאמות. היא מנהלת גם את תהליך ועדת הענן, כולל הגשות, חוות דעת, החלטות, פרוטוקולים אוטומטיים או ידניים, מעקב והיסטוריית החלטות.

המערכת כבר כוללת רכיבים המלווים את המשתמש במסע לענן. רכיבים אלה כוללים הנחיות FinOps ותגיות, סימולטור להפקת ארכיטקטורה מוצעת, וניהול תפוקות, אישורים ואבני דרך למערכות העולות לנימבוס. שלב ההמשך נדרש להרחיב כיסוי זה כך שיתמוך במסע המלא, מהערכת המוכנות ועד למעקב אחר המימוש.

הרחבה זו מחייבת חיבור בין תהליכים עסקיים, נתוני מקור והנחיות ממשלתיות. בין היתר, נדרשות אינטגרציות למרכב"ה, מערכת איתם, ה-IDP הממשלתי, קטלוג מוצרי נימבוס ומאגר מפת הדרכים. כל חיבור ישפיע על תהליך עסקי, הרשאות, איכות נתונים ותיעוד החלטות, ולכן יטופל כחלק מה-Spec ולא כפעילות טכנית מבודדת.

יכולות AI יכולות לסייע בתוך תהליכים אלה, אך אינן תחליף לשיקול דעת מקצועי, למדיניות או לאישור גורם מוסמך. תפקידן יהיה לאסוף הקשר, להציע טיוטה, להסביר דרישה ולהפנות למקור. החלטות, נתונים מחייבים ופעולות בעלות השפעה יישארו בשליטה אנושית ובהתאם למדיניות המשרד.

3. עקרונות הגישה שלנו

  • נמשיך את הקוד הקיים ואת הארכיטקטורה הקיימת, ונבצע שינוי מבני רק לאחר ניתוח צורך, חלופות ואישור.
  • לפני כל שינוי ראשון, Agent יבצע Discovery של בסיס הקוד, מודולי Next.js ו-React, בדיקות Playwright, אינטגרציות, תלויות ומודל הנתונים.
  • ה-Spec יהיה מסמך עברי קריא למנהל המוצר. הוא יהיה החוזה בין הצורך העסקי, העיצוב, המימוש, הבדיקות והקבלה.
  • כללים עסקיים, משקלים, פרמטרים ותוכן מאושר ינוהלו ככל הניתן כנתונים ולא כקוד. כך, לדוגמה, שאלות ומשקלים במחשבון ינוהלו בטבלה חיצונית עם מנגנון ניהול מתאים.
  • במקרים מתאימים, ניישם דפוס Rules-as-Data עם כללים ופרמטרים דטרמיניסטיים. היישום יותאם למודל הממשלתי, להרשאות ולבקרות הנדרשות.
  • הדיזיין סיסטם הממשלתי, נגישות AA והתאמה ל-Mobile ייכללו מהמסך הראשון ולא כשלב תיקון מאוחר.
  • תיקונים ותוספות יתחילו בעדכון Spec, Plan, Tasks ובדיקות. הקוד יותאם לאחר מכן, כדי למנוע סטייה בין התיעוד לבין היישום.
  • כל PR יעבור Code Review אנושי. Agent אינו מאשר קוד של עצמו, ואינו מחליף אחריות מקצועית של מפתח או מאשר מטעם המשרד.
  • כל רכיב יהיה עקיב מדרישה ועד מסירה: מזהה דרישה, משימה, תיעוד הפעלת Agent, PR, בודק אנושי ותוצאות בדיקות.

שיטת העבודה המפורטת, מבנה מסמכי ה-Spec, שערי האיכות, ניהול ההקשר והעבודה עם סוכנים מפורטים במסמך המתודולוגיה המצורף. במסמך זה אנו מיישמים את השיטה לצורכי מערכת "עולים לענן".

5. שלב ראשון: מימוש ועלייה לאוויר

קידוד מתוך Spec מאושר

המימוש יתחיל רק לאחר אישור ה-Spec העסקי ומסמך ארכיטקטורת הפתרון. Agent יפעל על מסמכים מאושרים ועל ההקשר הפרויקטלי. המפתח האנושי יוודא שהקוד נותן כיסוי מלא לדרישות, לתרחישי הקצה ולדרישות הלא-פונקציונליות.

כל שינוי יבוצע בענף עבודה מבודד ויוגש כ-PR. ה-PR יכלול קישור לדרישה, לשינוי ב-Spec, לבדיקות ולתיעוד. לא יתבצע מיזוג ללא Code Review אנושי ובדיקות נדרשות.

בדיקות

תכנית הבדיקות תגזור לכל דרישה תרחישי מסירה וקבלה. היא תכלול בדיקות יחידה, API, אינטגרציה, פונקציונליות, E2E ב-Playwright, בדיקות ויזואליות, בדיקות ידניות לפי סטנדרט המערך ובדיקות אבטחת מידע. נרחיב את תשתית Playwright הקיימת במקום ליצור תשתית מקבילה ללא צורך.

כל פיתוח חדש יכלול בדיקות רגרסיה. הבדיקות יורצו ב-CI/CD ויתועדו עם תוצאות, כיסוי, קריטריוני מעבר ודירוג קריטיות לתקלות. תאימות Mobile תיבדק בהתאם לסטנדרט המערך, לרבות iOS ו-Android עד שלושה דורות אחורה.

בכל יכולת AI, נגדיר Evals לפני שחרור. מערך הבדיקות יכלול דוגמאות ייצוגיות, מקרי קצה, ניסיונות להפקת מידע לא מורשה, בדיקת הפניות למקורות ובדיקת עקביות. ציון Evals לא יהיה תחליף לאישור אנושי בתהליך עסקי רגיש.

CI/CD בין סביבות

הפריסה תנוהל בין סביבות dev, test, pre-prod ו-prod, בהתאם לאזור הנחיתה, למדיניות המשרד ולתשתיות שיועמדו לפרויקט. סביבות פיתוח ובדיקה לא יכילו נתוני אמת. לצורכי פיתוח, בדיקות והדגמות נשתמש בנתונים סינתטיים.

קידום גרסה יתבצע דרך CI/CD בלבד, עם בדיקות, סריקות, ניהול גרסאות ותיעוד תצורה. כתיבה לייצור, מחיקת משאבים ושינויים ב-IaC יחייבו שלב Pipeline עם אישור אנושי מפורש. לאף Agent לא יהיו הרשאות ייצור ישירות.

ליווי בדיקות קבלה ובדיקות חדירה

נכין תסריטי בדיקות מסירה וקבלה לאישור המערך לפני ההרצה. נסייע בבדיקות שהמערך או צד שלישי מטעמו יבצעו, לרבות Code Review, בדיקות ביצועים, בדיקות אבטחת מידע ומבדקי חדירה.

ממצאים יתועדו, יתועדפו ויטופלו בתהליך מבוקר. תיקון יתחיל בעדכון ה-Spec הרלוונטי, יכלול בדיקת רגרסיה, ויעבור שוב את שערי האיכות הנדרשים לפני קידום.

תיעוד וקוד מקור

המסירה תכלול את קוד המקור, היסטוריית הגרסאות, מסמכי Spec, ארכיטקטורה, תיעוד ממשקים, תיעוד IaC, תיעוד בדיקות, תיעוד תצורה ותיעוד שינויים. קוד יתועד ברמת המתודה או הסקריפט, בהתאם לסטנדרט המשרד.

התיעוד יתעדכן כחלק מכל PR ולא בדיעבד. כלל החומרים ינוהלו בסביבת הפרויקט המשותפת למערך ולספק, בהתאם להנחיות המשרד.

7. יכולות AI בתהליכים העסקיים

היכולות הבאות הן כיוונים לבחינה משותפת עם מנהל המוצר. מימושן, היקפן וסדרי העדיפויות ייקבעו רק לאחר אפיון, בדיקת מקורות נתונים, אישור אבטחת מידע והגדרת קריטריוני קבלה.

9. ניהול, דיווח ושקיפות

נקיים ישיבות עבודה שבועיות עם צוות הפיתוח ומנהל הפרויקט מטעם המערך. אחת לחודש נקיים ישיבת סטטוס הכוללת התקדמות מול תכנית העבודה, סיכונים, החלטות נדרשות, איכות, תקלות, תלויות ושינויים צפויים.

למערך תינתן גישה למערכת ניהול המשימות של הפרויקט. כל משימה תכלול סטטוס, בעלות, קישור ל-Spec, PR, תוצאות בדיקות והחלטות רלוונטיות. לאחר פגישות יופץ סיכום הכולל החלטות, פעולות, אחראים ומועדים.

העבודה תתבצע ביחס של כ-70% מרחוק וכ-30% באתר, בהתאם לצורך בפגישות בעלי עניין, ראיונות עסקיים, סדנאות אפיון והעברת ידע. כלל חומרי הפרויקט ינוהלו בסביבה משותפת. הידע יישאר אצל המשרד באמצעות מסמכים, קוד, תיעוד, מפגשי העברת ידע ועבודה שקופה לאורך הפרויקט.

10. למה אנחנו

  • התאמה ישירה לבסיס הטכנולוגי המבוקש: Next.js, React, TypeScript, AWS, CI/CD ובדיקות E2E עם Playwright.
  • ניסיון בבניית פלטפורמות פרטיות ועמידה ברגולציה, שבהן דרישות מדיניות מתורגמות לכללים, תהליכים, הרשאות ובקרות. זהו עיקרון מרכזי במערכת "עולים לענן".
  • ניסיון בשילוב כללים ופרמטרים דטרמיניסטיים לצד מודלים, באופן המאפשר להפריד בין מדיניות, תהליכים ומימוש.
  • ניסיון בבניית מערכות multi-agent למוצרים, עם תפקידים מופרדים, זיכרון, RAG, כללים דטרמיניסטיים, לוגים של Prompts ותוצרים, Tracing וניתוב בין ספקי מודלים.
  • יותר משנתיים של עבודה עמוקה עם סוכני AI, ופיתוח יומיומי בשיטת SDD הכוללת חוקה פרויקטלית, עבודה מתוך Spec, Sessions מקבילים מבודדים ו-Review אנושי לכל שינוי.
  • ניסיון של מעל 20 שנים בפיתוח תוכנה ומעל 50 מוצרים שנבנו מאפס, לצד רקע מחקרי בהערכת מודלים, הסבר תחזיות ואופטימיזציה. רקע זה תומך בהגדרת Evals ובמדידת איכות AI מעבר לבדיקת Prompt בודד.
